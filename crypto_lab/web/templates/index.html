Security Insights

Why Caesar is breakable

  • Only 26 possible shifts (tiny key space) so attackers can brute-force every key in milliseconds.
  • It preserves letter frequencies, so a simple frequency analysis reveals likely shifts.
  • Any known word (like "THE") in the plaintext can reveal the correct shift immediately.

Why RSA requires proper key sizes

  • RSA security is based on the difficulty of factoring large integers.
  • Keys that are too small (e.g. 512- or 1024-bit) can be factored with modern hardware.
  • Today, real systems typically use at least 2048-bit or 3072-bit RSA keys.

Why hashing ≠ encryption

  • Encryption is reversible with the correct key; hashing is designed to be one-way.
  • Hashes are for integrity and password storage, not for hiding data you need to recover.
  • If you can "decrypt" a hash, it was either not a real hash or the password was guessed.

Why salting matters

  • A salt is random data added before hashing (e.g. hash(salt || password)).
  • Salts make precomputed rainbow tables useless and ensure identical passwords get different hashes.
  • Each user should have their own unique salt stored alongside the hash.

Real-World Use Cases

1. Password hashing simulation

In real systems, passwords are not encrypted and stored; they are salted and hashed. This demo uses a simplified model: SHA-256(salt || password).

2. Secure message exchange & MITM risk

Compare what an attacker on the network sees with and without TLS. This is a conceptual demo, not real TLS.

Without TLS, a man-in-the-middle can read and modify messages in transit. With TLS, the attacker only sees encrypted blobs and cannot safely tamper without breaking the connection.
